> **الحالة:** قيد التنفيذ على الفرع `fix/security-hardening-phase2`

> **المرجع:** الثغرات والأخطاء المسجلة في [`08-project-status.md`](08-project-status.md) + نتائج الجرد الموسَّع (القسم 1)

## 1) نتيجة الجرد الموسَّع

بعد المرحلة الأولى (S-01 إلى S-07) أجريتُ جرداً لكل الدوال التي تأخذ معرّفاً من الطلب (`{id}`):

| المقياس | القيمة |
|---|---|
| دوال تأخذ معرّفاً (API + Web) | 222 |
| بلا أي إشارة لفحص ملكية (فحص آلي) | 37 |
| بإشارة واحدة فقط | 40 |
| دوال عُلِّمت وراجعتُها يدوياً | الأخطر منها، ومعظم دوال المعلّم/الطالب/رئيس القسم |

> الفحص الآلي **كاشف وليس مثبِتاً**: كل ما عُلِّم يُراجَع يدوياً، وما لم يُعلَّم قد يخفي خللاً. لذلك تتضمن الخطة **اختبارات تفويض آلية** تثبّت النتيجة.

**أنماط الخلل المكتشفة (جديدة):**

| الرمز | الخلل | الأثر |
|---|---|---|

| N-16 | `ParentProfileController` غير مربوط بأي مسار (شيفرة ميتة) | يُحذف أو يُربط بتفويض |

## 2) المبادئ

1. **اختبار قبل الإصلاح:** لكل خلل اختبار Feature يفشل قبل الإصلاح وينجح بعده.
2. **مكان واحد للتفويض:** مساعد مركزي `App\Support\Access` بدل تكرار الفحوص.
3. **افتراضياً مرفوض:** لا يصل أحد إلى مورد إلا بإثبات ملكيته أو دوره.
4. **commit لكل مجموعة:** رسالة واضحة، وتشغيل الاختبارات قبل كل commit.
5. **لا كسر للتطبيق:** أي تغيير يمس سلوك Flutter يُعدَّل فيه التطبيق في نفس الدفعة.
6. **صدق التوثيق:** تُحدَّث `08-project-status.md` بما أُصلح فعلاً وما بقي.

## 3) مسارات العمل

### WS-A: الأساس (يُنفَّذ أولاً)
| # | المهمة | معيار القبول |
|---|---|---|
| A1 | بنية الاختبارات: قاعدة MySQL مخصصة للاختبار، **حارس يمنع تشغيلها على قاعدة غير `*_test`**، مساعدات لإنشاء الأدوار والبيانات | `php artisan test` يعمل ولا يمس القاعدة الحقيقية |

### WS-B: التفويض في الـ API (N-01 إلى N-09، N-14 إلى N-16)

## 5) المخاطر وخطة التراجع

- كل مجموعة في commit مستقل، فالتراجع بـ `git revert <commit>`.
- التغييرات تُجرَّب على قاعدة اختبار منفصلة، ولا تُنفَّذ أي migration مدمِّرة.
- الإصلاحات التي قد تغيّر سلوك المستخدم (انتهاء التوكن، رابط Telegram الموقّع) مُعلَّمة في ملف الحالة، وتُجرَّب على جهاز قبل النشر.
